# Architecture rules and their gates

git-forest's architecture decisions live in [`docs/decisions/`](decisions/ADR_INDEX.md). This document says which of those rules a command enforces, where each rule is enforced, and what the enforcement does not prove.

One local command is the gate: `just check`. It runs, in order, `cargo fmt --check`, Clippy for both build channels (`stable` and `beta`) across the whole workspace, all tests for both channels including the policy tests in `crates/policy`, and the positive control in `scripts/policy-control.sh`. CI runs the same `just check`, so the local gate and CI cannot drift. Run it before every commit and before handing work back.

Rules come in three kinds. A **gated** rule fails `just check` when code breaks it. A **checkable** rule is verified by a reviewer with a search, because a mechanical check would cost more than it saves. A **judgment** rule needs a person to decide; this document states the criteria.

The gates exist to catch architectural drift in ordinary code: a person or an agent writing a print in a command, a clock read in a shared module or an import against the class direction without noticing the rule. They are not a defense against deliberate evasion. Each check stays as small as the drift it catches, so an unusual spelling that ordinary code does not use and that slips past a check is listed under "What the gates do not prove" rather than closed with more machinery. A check that refuses ordinary, correct code is a bug to fix.

An "ambient effect" is anything that reads or changes the outside world without being passed in: environment variables, process arguments, the working directory, the clock, the filesystem, processes, threads, the network or the standard streams. The gates detect the specific forms listed in each section below, not every possible route; "What the gates do not prove" lists the known gaps.

## Module classes

Every `.rs` file under the `src/` directory of every workspace member except the policy crate has exactly one class, listed in `MODULES` in `crates/policy/src/classification.rs` by its path from the repository root. The classification test takes the members from `cargo metadata` (see "Crate classes and edges"), walks the `src/` beside each one's manifest, an unclassified member's too, and fails when a file is missing from that list, listed twice, or listed but gone, when an entry is not under such a directory, or when a file's class is one its crate's class does not hold: a file of a Pure crate classified anything but Pure, a file of the Binary crate classified anything but Root or Pure, or a file of an Effectful or Edge crate classified Root (`crate_holds_module_class`). A member missing from `CRATES` has no crate class, so this last rule skips its files; the edges test reports the member.

- **Root**: `src/lib.rs` and the binaries in `src/bin/`. The composition root: it reads the process arguments, the environment variables `HOME`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME` and `PWD`, the working directory and the clock once, and passes them to the commands as data; it resolves the config and state file locations, loads configuration through `git_forest_ops::config`, dispatches commands, prints results, builds the update check's settings and decides exit codes. Root may import anything. The classification rule constrains declarations, not effects: what a Root file's source may contain is the Root profile's job ("Root effects"), and how it composes the commands is a checkable rule ("Root composition").
- **Shell**: `crates/update-check/src/lib.rs`, the update-check edge crate's one module: a self-contained update-check subsystem with its own effects (an HTTP call, a state file, a spawned background process). Shell imports Shared and Pure.
- **Command**: every file in `crates/forest/ops/src/commands/`: each command's observe and execute steps. Commands return typed results, defined with their renderers in the core, and do not print (ADR 0002). A command imports Shared, Pure and allowlisted Command modules.
- **Shared**: `crates/forest/ops/src/lib.rs`, `crates/forest/ops/src/config.rs`, `crates/forest/ops/src/forest.rs`, `crates/forest/ops/src/git.rs`. Helpers used across commands, and the ops crate's root, which only declares its modules. Shared imports Shared and Pure.
- **Pure**: `src/channel.rs` and `src/cli.rs` in the root package, and every file of the core crate: `crates/forest/core/src/lib.rs`, `crates/forest/core/src/config.rs`, `crates/forest/core/src/meta.rs`, `crates/forest/core/src/paths.rs` and the modules under `crates/forest/core/src/plan/`. None of the effects listed in "Pure modules" in their own source. Pure imports only Pure, plus allowlisted edges. `src/channel.rs` and `src/cli.rs` stay in the root package because `cli` reads the root package's version and both branch on the stable and beta features, which only the root package has.
- **TestSupport**: `crates/forest/ops/src/testutil.rs`, compiled only for tests. It is classified so that every file has a class, but it is not scanned.

Nothing except Root imports Root.

## Crate classes and edges

Every workspace member has exactly one crate class, listed in `CRATES` in `crates/policy/src/edges.rs`:

- **Pure** (`CrateClass::Pure { feature }`): a crate of Pure modules only, for one feature, living at `crates/<feature>/<role>/`. This is `crates/forest/core` (`git-forest-core`, feature `forest`): the forest's decisions, types and renderers.
- **Effectful** (`CrateClass::Effectful { feature }`): a feature's effectful workflow (observing and executing what the feature's Pure crate decides), living at `crates/<feature>/<role>/`. It depends only on Pure and Effectful crates of its own feature and on the external crates in `EFFECTFUL_ALLOWED_CRATES`. This is `crates/forest/ops` (`git-forest-ops`, feature `forest`): every command's observe and execute steps, the git wrapper, forest discovery and metadata I/O, and the config file's I/O. Its allowed crates are `anyhow`, `chrono`, `directories`, `libc` and `toml`. Its public surface is explicit re-exports only: the command entry points, renderers and the types the root names, four config functions (`default_config_path`, `xdg_state_dir`, `load_default_config`, `version_check_enabled`) and `resolve_forest_multi`. Every observe, plan and execute step, the git wrapper and the metadata and config-file helpers are private to the crate.
- **Edge** (`CrateClass::Edge`): a client of one outside protocol, living flat under `crates/`. It depends on no member and only on the external crates in `EDGE_ALLOWED_CRATES`. This is `crates/update-check` (`git-forest-update-check`), the update server client, whose allowed crates are `chrono`, `semver`, `serde`, `serde_json`, `toml` and `ureq`; the composition root passes it the running binary's version, names, channel, state file and enabled flag as one settings value.
- **Binary**: the package that builds the binaries, whose files are Root or Pure only, so effectful code lives in a library crate. This is the root package, `git-forest`.
- **Tooling**: a crate that checks the others and is never part of the product. This is `crates/policy` (`git-forest-policy`).

The full layout is in ADR 0017; what makes work a feature, and why the forest is the only one, is in `docs/candidate-features.md`.

`crates/policy/tests/edges.rs` runs `cargo metadata --format-version 1 --no-deps --offline`, which lists the members and the dependencies each one declares without the network and without touching `Cargo.lock`, and reads each member's `Cargo.toml` for the one fact `cargo metadata` does not report, its `[lints]` table. It fails when:

- a member is missing from `CRATES`, a package is listed in `CRATES` more than once (with one class or with several), or a `CRATES` entry is not a member: every member appears in `CRATES` exactly once;
- a Pure crate has a build script, or a feature crate (Pure or Effectful) does not live at `crates/<its feature>/<role>`;
- a member has a path dependency, of any kind, on a package that is not a member;
- a member depends on a Tooling crate, in any dependency table;
- a normal or build dependency between members goes against the direction: a Pure crate depends only on Pure crates of its own feature, an Effectful crate only on Pure and Effectful crates of its own feature, an Edge crate on no member, a Binary crate on any member except Tooling, and a Tooling crate on no member;
- a Pure crate has a normal or build dependency on an external crate that is not in `PURE_ALLOWED_CRATES` (`crates/policy/src/classification.rs`), or declares a feature of an allowed crate that the list does not pin for it. The pins cover both the features declared on the dependency and the features the crate's own `[features]` table forwards to it (`<dep>/<feat>` and `<dep>?/<feat>`, where `<dep>` is the name the manifest declares the dependency under, its rename if it has one); a `dep:<name>` entry or a bare feature name forwards nothing. The pins are `chrono`'s `serde`, `clap`'s `derive`, `serde`'s `derive` and `toml`'s `display`, `parse`, `serde` and `std` (declared with `default-features = false`; its `debug` feature, which prints parser events to standard error and reads color variables, is not pinned); `anyhow` has none;
- an Effectful crate has a normal or build dependency on an external crate that is not in `EFFECTFUL_ALLOWED_CRATES`, or an Edge crate on one that is not in `EDGE_ALLOWED_CRATES` (both in `crates/policy/src/edges.rs`), or an entry of either list is not declared, as a normal or build dependency, by any crate of its class. These two lists name crates only: features are not pinned, because code in these classes performs effects by design, and the list's job is which clients and libraries the class uses, not which capabilities;
- a member's manifest does not inherit the workspace lints, which takes a `[lints]` table containing `workspace = true`.

Dev-dependencies are exempt from the direction and from every allowlist, except that none may point at Tooling: a Pure crate's tests may use `serde_json` or a Binary crate without its production code depending on them.

Together with the compiler this decides what a crate's code can reach. Rust refuses a path into a crate missing from the crate's manifest, and Cargo refuses a dependency cycle, so a Pure crate cannot name the Binary crate, any effectful workspace code or an external crate outside the allowlist; an Effectful crate cannot name an Edge crate, the Binary crate or another feature's crates; and an Edge crate cannot name any member. Every message names the member, the rule and the fix.

## Import direction

`crates/policy/tests/direction.rs` computes, for every module except TestSupport, the crate-internal modules it refers to, and checks each edge against the class rules above. Edges are computed within one crate: a module's identity is its crate's directory and its path inside that crate, split at the file path's first `src` component, so each crate's `src/lib.rs` is that crate's `crate`, and known modules, classes and `ALLOWED_EDGES` entries are looked up in the module's own crate. A path into another workspace crate starts with that crate's name and is not an edge here: every module class may use a Pure crate, and the edges test checks the crate dependency itself. An edge is any path that starts with `crate::`, `super::` or `self::` in the module's production code, written inline or inside a `use` tree (`use super::rm::{self, X}` counts as `super::rm`). A path is read once, from its first segment, so `super::super::channel::APP_NAME` in `commands::rm` climbs two levels and is an edge to `channel`. `super` and `self` resolve against the module's own path plus any inline `mod name { ... }` blocks around them: inside an inline module `child` of `src/channel.rs`, `super::APP_NAME` refers to `channel` itself. Each path is cut back to the longest known module, so `crate::meta::read` is an edge to `meta`. Edges to the module itself, including its inline modules, and to its own child modules are dropped. Visibility qualifiers such as `pub(crate)` and `pub(in crate::commands)` are not edges. Code inside an inline module whose attributes include `#[cfg(test)]`, whatever its visibility and other attributes, is not production code and is skipped; so are comments and string literals.

Edges the class rules refuse but that are sanctioned are listed in `ALLOWED_EDGES`, each with a reason; all of them are inside the forest ops crate (`crate_dir` `crates/forest/ops`):

- `commands::ls`, `commands::rm` and `commands::status` import `commands::branch_state`, the helper shared by the commands that inspect worktree branches. This is a permanent boundary.
- `commands::reset` imports `commands::rm`, because reset observes and executes forest removal through rm's effectful helpers (observation, branch deletion, forest-directory removal); the removal plan and its decisions live in `crates/forest/core/src/plan/rm.rs`. Whether those helpers become a shared module is an open question (temporary).

An allowlist entry whose edge no longer exists fails the test too, so the list cannot go stale. A violation message names the edge, both classes and the rule, and says how to fix it: move the import, or add an `ALLOWED_EDGES` entry with a reason.

## Pure modules

A Pure module's production code may not contain any of the effects listed below. `crates/policy/tests/ambient.rs` scans each Pure module with a token-level scanner, so comments, strings and raw strings can neither hide nor fake a path, and aliases (`use std::env as e`), grouped imports, glob imports and raw identifiers are resolved. It reports:

- any use of `std::fs`, `std::env`, `std::process`, `std::net`, `std::time` or `std::thread`, inline or imported;
- standard input (`std::io::stdin` or `std::io::Stdin`);
- a `std::path` name with an effect: the `Path` methods that query the filesystem (`exists`, `try_exists`, `metadata`, `symlink_metadata`, `canonicalize`, `read_dir`, `read_link`, `is_file`, `is_dir` and `is_symlink`) and the function `absolute`, which reads the working directory. They are matched by name when called as a method, with or without a turbofish (`path.exists()`, `path.exists::<>()`), after `::` whether called or used as a value (`Path::exists(p)`, `.any(Path::exists)`, `std::path::absolute(p)`), and as the last segment of a `use` import (`use std::path::{absolute, Path};`). The scanner does not know types, so a method or item of another type with one of these names is reported too;
- a path into a dependency crate of the module's own package, meaning any key of that package's `Cargo.toml`'s `[dependencies]` or `[target.*.dependencies]` tables with hyphens read as underscores, unless the crate is in `PURE_ALLOWED_CRATES` in `crates/policy/src/classification.rs` or is a Pure workspace crate in `CRATES`. Today that list holds `anyhow`, which carries errors; `chrono`, which supplies date and time types (its clock reads are banned by `clippy.toml`); `clap`, which `src/cli.rs` and `crates/forest/core/src/meta.rs` use to derive argument types (parsing the arguments, which reads the process's arguments, happens in `src/lib.rs`); `serde`, which derives serialization; and `toml`, which parses and renders the config file's format. An allowed crate that no Pure module uses fails the test;
- `include!` and `#[path = ...]`, which pull Rust code into the module from a file the scanner does not read;
- `unsafe`, `extern`, `macro_rules!`, glob imports of `std` or `core`, importing or aliasing `std` itself, and non-ASCII identifiers.

`Path` and `PathBuf` are allowed as data; only the effectful path names above are reported. `include_str!`, `include_bytes!`, `env!` and `option_env!` are allowed: they are compile-time inputs, fixed when the binary is built, not effects at run time. (The qualified spelling `std::env!` is still refused, because the scan bans the `std::env` path.)

The core's `plan` modules hold the decide steps of `new`, `rm`, `reset`, `ls` and `init` and the result types and renderers of every command; the observe and execute steps stay in the forest ops crate's command modules, and so do the bodies of `status`, whose `git status` runs only where an earlier observation allows it, and `exec`, which streams the user's command: those two have result types and renderers in the core and no decide step.

When may a module become Pure? When its own production code has none of the effects above and it imports only Pure modules, or holds an allowlisted edge with a reason naming how that edge goes away. The config file's format, `expand_tilde` included, is Pure in `crates/forest/core/src/config.rs` because the composition root passes the home directory in, while reading and writing the file stay in the forest ops crate; likewise the metadata file's I/O (`read_meta` and `write_meta`) lives in `crates/forest/ops/src/forest.rs`, while the Pure types are in `crates/forest/core/src/meta.rs`. Reclassifying a module is a one-line change in `MODULES`; the ambient and direction tests then say whether it holds.

## Root effects

The Root profile of the ambient scan applies to the production tokens of every Root file (`src/lib.rs` and the binaries); `crates/policy/tests/ambient.rs` fails when it reports anything. It is the same token scanner as the Pure profile (`crates/policy/src/scan.rs`), and it reports:

- any use of `std::fs`, `std::net` or `std::thread`, inline or imported, and through aliases;
- any path through `std::env` other than the namespace itself (`use std::env;` is allowed, and every use through it is checked), `std::env::args_os` and `std::env::ArgsOs`, which read the process arguments the composition root parses, and `std::env::var`, `std::env::var_os` and `std::env::current_dir`, which read the environment variables and the working directory it reads once and passes in;
- the effectful `std::path` names, with the rules of "Pure modules";
- `include!` and `#[path = ...]`, `unsafe`, `extern`, `macro_rules!`, glob imports of `std` or `core`, importing or aliasing `std` itself or aliasing `core`, and non-ASCII identifiers, exactly as in Pure modules.

It does not report `std::process`, `std::time` or `std::io`, standard input included, or the clock: the composition root spawns `brew`, reads the clock and acquires the standard streams by design, and those calls stay banned by `clippy.toml` outside their sanctioned sites, which the positive control counts. `include_str!`, `include_bytes!`, `env!` and `option_env!` stay allowed. The `std::env` sanction is by name anywhere in a Root file: `clippy.toml` bans the three reads outside sanctioned sites, and the positive control counts the five reads in `main_entry` (three `var`, one `var_os`, one `current_dir`), so a sixth read changes the count. `std::env::temp_dir`, `home_dir`, `vars`, `set_var` and every other path through `std::env` stay reported.

## Root composition

Root composes: ops' public surface is explicit re-exports only; each `run` arm calls at most one command entry point and progress callbacks call no operation; Root adds no predicates over repository, forest or configuration state. The one exception is the update check's flag: the root reads `version_check.enabled` through `config::version_check_enabled` to build the update-check settings and to gate the explicit `version --check`; the cached-notice entry point enforces the same flag itself, and the background check ignores it. No gate checks this; a reviewer checks it with three searches:

- `rg -n '^\s*pub (use|fn)' crates/forest/ops/src` shows ops' public surface; read it from the code. The surface is the `pub use` lists in `crates/forest/ops/src/commands/mod.rs` and the `pub fn` items of `config.rs` and `forest.rs`; a `pub fn` or `pub use` inside a private command module is reachable only through `commands/mod.rs`'s lists, which is how the command modules re-export the core's result types and renderers that the root names. Public data declarations count too: `rg -n '^\s*pub (struct|enum|type)' crates/forest/ops/src/{config,forest}.rs` shows the types those public modules expose, which should be only the ones the root names or returns (the forest results and the two values the root builds from what it read, `Environment` and `WorkingDirectory`; the config the root loads is the core's `ResolvedConfig`); `commands/mod.rs`'s reset line also names `ResetPaths`, the paths and home directory a reset acts on. A new name in either search widens the surface and needs a reason.
- `rg -n 'commands::cmd_|git_forest_ops::' src/lib.rs` shows the root's command call sites; compare them with the dispatch arms of `run` and their enclosing bodies.
- `rg -n '\b(if|match)\b' src/lib.rs` shows the root's predicates. A predicate that reads repository, forest or configuration state to decide whether or how an operation proceeds is a violation; command-line parsing, presentation branches, the existing completion mappings (`errors.is_empty`, `failed > 0`, `confirm_required` and `failures.is_empty`) and the two `Enablement` branches of the update check are not. Today the search prints about 48 lines, nearly all parsing or presentation.

The searches are exhaustive for the ordinary form because of a convention: effectful entry points are called directly by qualified path in Root (`commands::cmd_ls(...)`), never imported by name, stored or passed as values.

## No production traits

ADR 0002 keeps the call graph shallow: no traits, dependency injection or ports-and-adapters machinery. `crates/policy/tests/traits.rs` fails when production code declares a trait (`trait` followed by a name, outside test modules). Implementing a trait from another crate, such as `impl std::fmt::Display for X`, is fine.

When does a trait earn its place? Only when production code has more than one real implementation that callers must treat the same way. Test doubles are not a reason, because tests run against real git repositories (ADR 0007). Adding one is a design decision: record it in an ADR and add an entry to `ALLOWED_TRAITS` in `crates/policy/tests/traits.rs` with the reason. An entry whose trait no longer exists fails the test.

## Ambient reads

The root `clippy.toml` bans, through Clippy's `disallowed-methods`, the functions that read or change the process's surroundings: `std::env::var`, `var_os`, `vars`, `vars_os`, `args`, `args_os`, `current_dir`, `set_current_dir`, `current_exe`, `home_dir`, `set_var` and `remove_var`; `std::process::exit`, `abort` and `Command::new`; the clocks `chrono::Utc::now`, `chrono::Local::now`, `std::time::SystemTime::now` and `std::time::Instant::now`; and the `ureq` request functions `ureq::get`, `post`, `put`, `delete`, `head`, `options`, `connect`, `patch`, `trace` and `run`, with the `ureq::Agent` methods of the same names, whose one sanctioned caller is the update check in `crates/update-check/src/lib.rs`. Each entry carries a reason saying where the call belongs, and Clippy prints it with the error. Clippy resolves paths by definition, so aliases, glob imports and re-exports are caught. The same file bans the standard stream handles; see "Printing".

A sanctioned site carries `#[expect(clippy::disallowed_methods, reason = "...")]` on the enclosing function (or, for the update-check edge crate, one crate-level `#![expect(...)]` in `crates/update-check/src/lib.rs`). `#[expect]` is used instead of `#[allow]` because a stale `#[expect]` fails the build with "this lint expectation is unfulfilled": when the call goes away, the attribute must go too. Sanctioned sites are of two kinds. Permanent boundaries are where the rules say an effect belongs, and stay as long as the architecture does: the composition-root functions `main_entry`, `run` and `output` in `src/lib.rs`, the git wrapper functions `git`, `ref_exists` and `is_git_repository` in `crates/forest/ops/src/git.rs`, `exec`'s spawn of the user's command, and the policy crate's `cargo metadata` call in `crates/policy/src/metadata.rs`; their reasons name the boundary. Temporary exceptions are effects that a planned change will move; their reasons name that change, and "Planned follow-ups" lists them. None remains today. Reason text is reviewed, not checked: the build enforces that every `#[expect]` still fires, not what its reason says.

Tests are exempt. The ops crate's unit tests get a crate-level `#![cfg_attr(test, allow(clippy::disallowed_methods, ...))]` in `crates/forest/ops/src/lib.rs`; the integration tests keep their crate-root `#![allow(...)]` in `tests/cli_test.rs`. Both build real git repositories by design, and the CLI tests also read `PATH`. Production code stays linted because Clippy also checks the library in its normal, non-test build, where the `cfg_attr` does not apply. The exemption covers only the ops crate: a `cfg_attr` applies to the crate it is in. The root package has no unit tests and no exemption. The core crate's unit tests need none, because they call no banned method and print nothing. The update check's unit tests run under its crate-level `#![expect(...)]`, which covers their clock reads. If a member's tests ever need one, it is a crate-level `#![cfg_attr(test, allow(...))]` in that member's `src/lib.rs`, with a reason.

`clippy.toml` must stay the only one in the workspace: a per-crate `clippy.toml` replaces the root file for that crate instead of extending it.

## Printing

Only the shell uses the standard streams: commands return data and `src/lib.rs` prints it (ADR 0002). Two gates enforce this. The `[workspace.lints.clippy]` table in the root `Cargo.toml`, which every member inherits through `[lints] workspace = true` (the edges test requires that table of every member), turns on `print_stdout` and `print_stderr`, and `just check` runs Clippy with `-D warnings`, so `println!`, `print!`, `eprintln!` and `eprint!` fail outside sanctioned sites; the same table turns on `dbg_macro`, so `dbg!`, which prints to standard error, fails anywhere in product code (it has no sanctioned site). The root `clippy.toml` bans `std::io::stdout`, `std::io::stderr` and `std::io::stdin`, so acquiring a stream handle to write or read through it fails too, with the reason "acquire standard streams only in src/lib.rs". Sanctioned sites carry `#[expect(clippy::print_stdout, ...)]`, `#[expect(clippy::print_stderr, ...)]` or `#[expect(clippy::disallowed_methods, ...)]`: `run`, `output`, `print_json` and `report_failure` in `src/lib.rs` (`run` also flushes standard output while printing progress, and hands standard error to `exec`'s child under `--json`), and `crates/update-check/src/lib.rs`. `allow-print-in-tests = true` and `allow-dbg-in-tests = true` in `clippy.toml` exempt test code from the print and `dbg!` lints; the test exemptions described in "Ambient reads" cover the stream handles.

## Positive control

A ban that silently stops firing looks exactly like a codebase with no violations. `scripts/policy-control.sh` (run by `just policy-control`, part of `just check`) proves the bans still work. It runs Clippy on the library and binaries for the stable channel with `--force-warn` on `clippy::disallowed_methods`, `clippy::print_stdout` and `clippy::print_stderr`, which makes every sanctioned site warn even though its `#[expect]` silences it in the normal build. It reduces each warning to its file and message, counts them, and compares the result with `crates/policy/control-expected.txt`; any difference fails with a diff. It also fails if Clippy reports that a `clippy.toml` path does not refer to a reachable function, so a typo in an entry whose path starts with a loaded crate, such as `std` or `chrono`, cannot disable it silently (for unloaded crates, see "What the gates do not prove").

The script forces `CARGO_TERM_COLOR=never` (CI sets `always`, and colour codes would hide every warning from the parser) and `LC_ALL=C` (so the sorted counts match on macOS and Ubuntu).

## Planned follow-ups

Temporary exceptions name the change that removes them; together they are the to-do list the build enforces. No temporary sanctioned site remains today; the open question below stays. Permanent sanctioned boundaries are not on this list: the composition-root functions in `src/lib.rs`, the git wrapper in `crates/forest/ops/src/git.rs`, `exec`'s spawn of the user's command, the policy crate's `cargo metadata` call, the `branch_state` helper edges and the entries in `PURE_ALLOWED_CRATES`. Reason text is reviewed, not checked.

## Changing the rules

**Adding a module.** Create the file and add it to `MODULES` in `crates/policy/src/classification.rs` with its class. The classification test fails until you do. A module added to the root package must be Root or Pure; effectful code goes into a library crate. If the new module needs an import the class rules refuse, either restructure or add an `ALLOWED_EDGES` entry whose reason names the permanent boundary it is or the change that removes it.

**Adding an exemption.** Put `#[expect(<lint>, reason = "...")]` on the narrowest enclosing item, listing only the lints that actually fire there, with a reason that names the permanent boundary, or, for a temporary exception, the follow-up removing it. Then update `crates/policy/control-expected.txt`: the positive control fails with a diff showing the new count, which is the line to change. Add a temporary exception's follow-up to "Planned follow-ups".

**Adding a banned method.** Add an entry to `disallowed-methods` in the root `clippy.toml` with a reason saying where the call belongs. If the method has sanctioned call sites, exempt them as above; their lines in `crates/policy/control-expected.txt` prove the path resolves. If it has no call site anywhere, Clippy's reachable-function check still proves that a path under a loaded crate resolves; nothing proves a path under an unloaded crate (see "What the gates do not prove").

**Allowing a crate in Pure modules.** Add it to `PURE_ALLOWED_CRATES` in `crates/policy/src/classification.rs`, with a comment saying why the Pure module needs it and why what it uses is not an effect. An entry that no Pure module uses fails the test.

**Allowing a crate in an Effectful or Edge crate.** Add it to `EFFECTFUL_ALLOWED_CRATES` or `EDGE_ALLOWED_CRATES` in `crates/policy/src/edges.rs`, with a comment saying why that crate's code needs it; an entry no crate of the class uses fails the test.

**Adding a crate.** Put a feature crate (Pure or Effectful) at `crates/<feature>/<role>/` and an Edge crate flat under `crates/`, and add its files to `MODULES` with their classes. Give its `Cargo.toml` `version = "0.0.0"` and `publish = false`, so `just release` touches only the root package, and a `[lints]` table with `workspace = true`. Add it to `[workspace] members` in the root `Cargo.toml` and to `CRATES` in `crates/policy/src/edges.rs` with its class; the edges test fails until it is there. Depend on it by path without a `version` key (`git-forest-<name> = { path = "crates/<feature>/<role>" }`), so the release version `sed` cannot match the line. Refresh `Cargo.lock` (`cargo check --workspace`) and commit it with the change, because `just check` runs Cargo with `--locked`.

**Adding a trait or an allowed edge.** See "No production traits" and "Import direction". Every allowlist rejects entries that are no longer used: the allowed edges, the traits, and the Pure, Effectful and Edge crate lists.

## What the gates do not prove

- Bare child-module paths are not followed by the direction scan: a path that starts with a child module's name, such as `init::x` or the `pub use rm::{...};` re-exports in `crates/forest/ops/src/commands/mod.rs`, is ignored. Only `crate::`, `super::` and `self::` paths are checked.
- Macro-generated code and text pulled in with `include!` are not scanned outside Pure and Root modules; the scanner reads source tokens, not expanded code. In Pure and Root modules, `macro_rules!` and `include!` are refused outright.
- The purity scan matches names, not resolved types or calls. It does not see an effect reached through an allowed crate (clap's `Parser::parse` reads the process's arguments, so a Pure module calling it would not be reported) or through trait dispatch.
- Output routes other than the print macros, the stream handles and `dbg!` are not gated: panic messages reach standard error, and Shared or Command code, where filesystem access is by design, could open `/dev/stdout` or a similar device through `std::fs`, or write to descriptors 1 and 2 through `libc` or the `unsafe` raw-descriptor APIs. The `dbg_macro` lint has no sanctioned site, so the positive control cannot show it still fires; its proof is the break-once check recorded when it was added.
- The dependency scan reads each package's `Cargo.toml` line by line and takes each dependency's package key, hyphens read as underscores, as the name code uses. It does not decode TOML quoting or escapes in table names and keys (a quoted table-name segment such as `["dependencies".review_dep]`, or an escaped key such as `"review_\u0064ep"`; a plain quoted key such as `"quoted-name"` is read correctly), does not read top-level dotted keys such as `dependencies.foo = "1"`, and does not know that a dependency whose library target sets another `name` is used under that name. A dependency declared those ways escapes the crate rule in Pure modules. The guard test knows only today's eight names in the root `Cargo.toml`.
- The edges test reads the dependencies each member declares, not transitive ones, and checks the features a Pure crate declares, not the set Cargo unifies across a workspace build. Feature unification across the workspace is not checked: another member that enables more features of a crate a Pure crate also depends on (the Binary crate's own `clap` features, say) widens what the Pure crate's code compiles against in a workspace build, without a report. A `dep:<name>` entry is not read as forwarding: the optional dependency it enables is checked like any other dependency, by the features declared on it.
- Default features are not checked, so a Pure crate keeps an allowed crate's default features, `chrono`'s clock among them; `clippy.toml` bans the clock reads. `toml`'s default features equal its four pinned ones, so a core manifest without `default-features = false` would pass the edges test and enable nothing more.
- Dev-dependencies are exempt from the crate direction and from every allowlist, except toward Tooling.
- The Effectful and Edge lists name crates and do not pin features, so a feature added to an allowed crate's declaration is not reported.
- The Binary crate has no external allowlist: a crate added to the root `Cargo.toml` can be named from `src/lib.rs`. The root package's Pure modules stay held to `PURE_ALLOWED_CRATES` by the source scan (see "Pure modules").
- The lints fact is read from manifest text, and only the `[lints]` table form is recognized: a dotted `lints.workspace = true` key is reported as missing.
- Network requests outside `crates/update-check/src/lib.rs` fail through the `ureq` bans; another HTTP client added to the ops crate fails its allowlist, and one added to the root `Cargo.toml` would need its own ban entries. Filesystem access is reported only in Pure and Root modules; commands read and write forests by design.
- The Root profile sanctions `std::env::var`, `std::env::var_os` and `std::env::current_dir` by name anywhere in a Root file; that they are read once, in `main_entry`, is proven by the positive control's count, not by the scan.
- The classification rule constrains which module classes each crate declares, not what the code does: it is not proof of composition semantics. The Root profile checks source forms in Root files, not expanded code, resolved receiver types or effects reached behind a dependency (a Root file calling an ops function that reads a file is not reported). Rust visibility prevents access to ops' private items but not the growth of its public surface. Neither gate prevents a root function from calling two commands or deciding on supplied values; the checkable rule in "Root composition" covers those.
- The policy scans read each product crate's `src/` and manifest; integration tests, the policy crate itself and the `worker/` directory are not classified.
- A `clippy.toml` entry with no call site anywhere is covered only by Clippy's own "does not refer to a reachable function" warning, and that warning is not emitted when the path's first segment names a crate that is not loaded, so such an entry could do nothing unnoticed. This was confirmed on Clippy 0.1.95 by an experiment that replaced an unused entry with a path under an unloaded crate and saw no warning.
- The Rust toolchain is not pinned. A future stable Clippy may add lints that fail `-D warnings`, as it already could before these gates existed.
- CI installs `just` from the Ubuntu archive on an `ubuntu-24.04` runner; that step was untested when the gates were introduced, and only a push or pull request exercises it.
